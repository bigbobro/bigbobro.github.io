这周盯下来，我一个新模型名都没记住。

真正在动的是几件更底层的事。harness 以前是藏在框架里的胶水，现在得让人读得懂、审得了、随时能改；长时代理的及格线，从「最后跑没跑通」挪到了「每一步能不能验」；Coding Agent 把你的代码读走之后送去了哪里、存成什么样，开始被人一行行扒。浏览器也悄悄成了代理的「手」，查资料、点界面、验结果，都收进同一个回路。研究侧还有一条不太一样的：GenCeption 说，视频生成的预训练可能会变成通用视觉感知的底座。

时间范围是 2026-W29：2026-07-13 到 2026-07-19。

## 一句话判断

这周的关键词是「可审计」。

代理能力还在涨，但这周值得记的几条，讲的都是同一件事的不同侧面：它某个行为到底是哪段实现造成的，你能不能看懂（harness）；它中间的每一步，你能不能验（长时任务）；它把数据发去了哪儿，你能不能查（上传行为）。

所以接下来该盯的，是这几样有没有变成产品的默认配置：harness 可读、过程可验、数据流可查。

## 1. 代理 harness 开始变成要被人读的工程系统

研究侧提出了 Harness Handbook，把执行、权限、安全这些行为问题，对应到具体的提示词、工具、状态、配置和遥测；阅读侧随即把它读成一张地图，能从代理的某个行为倒推回是哪段代码实现的。harness 不再是藏在框架里的胶水，它是要被人读、被人审、被人持续改的系统。

我把它排在第一位，是因为代理能力越来越依赖 harness，维护的瓶颈就会从「模型够不够强」，挪到「团队看不看得懂某个行为是哪段实现造成的」。一张能倒推的行为地图，直接决定改动、审计和安全复盘要花多少成本。

Harness Handbook 做的事是：把自然语言层面的执行、权限和安全问题，对应到提示词、工具、状态逻辑、配置和遥测，并且明确说，还在演化中的 harness 应该被当成一个可读、可导航、可编辑的工程对象。

来源：[Harness Handbook 论文](https://huggingface.co/papers/2607.13285)，[Harness Handbook 项目](https://ruhan-wang.github.io/Harness-Handbook)

## 2. 长时代理要的是过程级验证，而不只是终态打分

研究侧用 Long-Horizon-Terminal-Bench 把长时终端工作拆成 46 个跨九类的状态化任务，用细粒度奖励记下中间进度；阅读侧注意到，它公开仓库里藏了验证器，会自己重建产物再检查一遍，不听代理自报。两边合起来，把「能连续干很久」这件事，改成了「每一步都得能验」。

它值得单列，是因为只看最后过没过，会盖掉代理在长链路里走偏、侥幸蒙对、或者根本爬不回来的真实问题。过程级验证让长时代理的进步能被诊断，生产里用起来也更接近可控工程。

这个基准发布了 46 个跨九类的长时终端任务，用细粒度奖励刻画部分完成，由隐藏验证器重建并检查产物。

来源：[Long-Horizon-Terminal-Bench 论文](https://huggingface.co/papers/2607.08964)，[Long-Horizon-Terminal-Bench 仓库](https://github.com/zli12321/LHTB)

## 3. 视频生成模型正在变成通用视觉骨干

研究侧提出 GenCeption，把预训练的视频生成扩散骨干，改造成一个由文本指令控制的统一视觉感知系统；阅读侧也很快抓住了那个反转：生成器可以反过来服务感知。这条的重点不在又多了个视频模型，而在视频生成预训练开始承担通用视觉学习的底座角色。

我觉得它重要，是因为生成训练拿到的时空先验和视觉语言对齐，如果真能迁到感知任务上，视频模型的价值边界就从做内容扩到了通用视觉系统，训练投入怎么算、模型怎么复用，都会跟着变。

GenCeption 把预训练视频生成扩散骨干改造成文本可控的统一视觉感知系统。研究认为，视频预训练同时给了三样东西：时空先验、视觉语言对齐，以及往上扩的路径。

来源：[GenCeption 论文](https://huggingface.co/papers/2607.09024)，[GenCeption 项目](https://genception.github.io/)

## 4. 专用对抗模型进了安全训练闭环

应用侧把 GPT-Red 描述成一个专门去攻击其他模型、找隐藏指令劫持路径的内部模型；阅读侧补上了它怎么迭代生成对抗提示，再把攻击样例回灌进训练。两个来源层指向同一个发布页，说的是同一件事：安全测试正从人工写样例，变成模型驱动的持续攻击循环。这也是本周共振最强的一条。

我留意它，是因为对抗测试一旦能自动扩展，安全团队就能更频繁地捞出长尾攻击，再把它们变成训练数据。反过来，这种闭环会不会泛化、会不会自己制造出新的盲点，也就更需要评估了。

GPT-Red 被用来迭代生成对抗提示、规模化暴露漏洞。候选材料称，把它的攻击纳入训练之后，GPT-5.6 Sol 在一项困难提示注入基准上的失败次数降低了六倍。

来源：[GPT-Red 安全训练](https://openai.com/index/unlocking-self-improvement-gpt-red)

## 5. 代码代理的默认上传行为，成了信任边界

应用侧记录了 Grok Build 因为默认上传代码挨了骂、随后宣布 CLI 开源；阅读侧则出现了一份技术审计，去查它实际传了什么、存在哪。两边一起追问的，不只是企业的代码治理，还有任何一个 Coding Agent 用户都得自己确认的事：它读了什么、发到哪里、以什么粒度留存，以及这些能不能被外人核验。

我把它放进头部，是因为 Coding Agent 碰得到的不只是代码，还有凭据，以及通过文件、浏览器或工具权限能够到的其他值钱东西。这事不专属于企业：个人开发者的钱包、支付信息、私人资料，只要落在代理够得着的范围里，一样会暴露。开源只解决一部分可检查性，真正决定你敢不敢信它的，是默认数据流、最小化传输、权限隔离和存储说明。

经过是这样：Grok Build 因默认上传代码受到反弹，随后开源了 CLI；一份审计称，它会原样传输读取的文件，并把整个仓库上传到 Google Cloud Storage，同时没有证据表明这些数据被用于训练。

来源：[Grok Build 开源回应](https://simonwillison.net/2026/Jul/15/grok-build)，[Grok Build 传输审计](https://gist.github.com/cereblab/dc9a40bc26120f4540e4e09b75ffb547)

## 值得继续跟踪

下面这几条本周也有动静，但要么还只是单层、要么热度还没变成能验证的使用，我先放着逐周看。

### 编码代理把浏览器纳入同一执行回路

应用侧和阅读侧都显示，Claude Code 已经把内置浏览器纳进了工具层：它能读网页、点界面，还能在本地开发页面上检查结果。浏览器跑在沙箱里，会话保不保留可以自己配。重点不只是多了个功能，而是 Coding Agent 开始拿浏览器当「手」，把查资料、动手操作、验结果收进同一个回路。对 Coding Agent 来说，浏览器顺不顺手，直接决定它能不能高效查资料、操作网页工具、核验自己写的代码跑出来的界面；这条回路可靠了，它交出来的才是能检查的活。站点权限、登录态和会话持久化，是随之而来的新控制面。下周我会看搜索和页面读取稳不稳、点击和表单顺不顺手、执行结果能不能可靠检查，还有跨站登录、本地页面测试、失败恢复和权限隔离的真实表现。

来源：[Claude Code 浏览器公告](https://x.com/ClaudeDevs/status/2075635283211772279)，[Claude Code 浏览器摘要](https://threadreaderapp.com/thread/2075635283211772279.html)

### 开放模型开始有了能跑的本地代理壳层

应用侧的 GitHub 趋势把 Open Interpreter 标成面向 Kimi K3 等开放模型的编码代理；阅读侧强调它能在本地跑，还能测网页或原生应用界面。这条信号落在运行时，不在模型榜单：开放权重正在被装进真能执行的代理工作流里。开放模型能不能进入实际工作，越来越取决于本地工具调用、界面测试和部署体验，光是权重能下载已经不够；本地壳层也把数据和执行的控制权更多留给了用户。下周看仓库的周度增长能不能续上，以及有没有独立的本地网页或原生应用测试案例，能证明热度真的变成了稳定使用。

来源：[Open Interpreter 仓库](https://github.com/openinterpreter/openinterpreter)

### 代理记忆从被动检索走向主动提醒

阅读侧这周同时冒出两种主动记忆的做法：一种是让独立的记忆代理盯着关键状态，等信息快丢的时候提醒行动代理；另一种是从连接源不断更新一个本地 wiki，再把相关上下文喂给代理。具体说，一项研究报告称，独立记忆代理不用改行动模型，就能提高长时基准的通过率；OpenWiki Brains 则从 Gmail、Notion 这类连接源维护一个可复用的本地 wiki。这还是单层信号，但两者都指向同一个新问题：记忆该在什么时候主动开口。把记忆维护和行动模型拆开，意味着不重训底层模型也可能改善长任务表现，而难点会转到提醒时机、过期信息和噪声控制上。下周关注主动记忆能不能在更多长时基准上复现增益，以及生产工具会不会公开提醒准确率、过期信息和干扰率这些指标。

来源：[长时代理主动记忆研究](https://arxiv.org/abs/2607.08716)，[OpenWiki Brains](https://www.langchain.com/blog/introducing-openwiki-brains-general-purpose-wiki-memory-for-agents)

## 没有放进主线的信号

有几个主题这周也值得知道，但跨层证据不够，我没有把它们提升为头部信号：

- **Inkling 开放模型发布**：应用侧和阅读侧主要在重复同一个发布，候选材料还指出它的能力尚未接近领先的开放模型，目前缺少独立采用或效果证据。
- **GPT-5.6 Sol 话题簇**：材料混合了设计表现、数学任务、电脑操作和用量政策等不同后果，没法用一个结果级的变化准确覆盖。
- **GLM-5.2 跨层提及**：研究侧把它用在长上下文强化学习的执行栈里，应用侧讨论的是视觉补全和自托管，共享一个名字并没有形成同一个变化。
- **Codex 上下文变化与仓库热度**：仓库趋势和上下文窗口缩减属于不同结果，不能只因为项目名相同就合并。
- **Gemma 4 系列更新**：31B 的提示处理与工具使用更新，和面向手机 TPU 的 E2B 版本，处在不同的规格与部署场景。
- **泛化的 Agent Skills 热点**：分层搜索技能和内容蒸馏技能只共享一个宽泛标签，方法和产出都不同，构不成可靠共振。
- **OpenClaw GUI 生态**：研究材料确实扩展了 OpenClaw，但应用材料只是把另一个产品称为竞争者，缺少同一方法或结果的跨层证据。
- **由人塑造的 AI 使命宣言**：两层材料重复的是同一份使命宣言，还没有产品行为、用户反馈或可观察结果来支撑提升。

## 可选阅读

### 蒸馏的是强化学习带来的那点变化，不是弱模型本身

这是研究侧的一条单层论文信号。Direct-OPD 先在较小的模型上跑更便宜的强化学习，再拿训练前后两个检查点当教师对，用更强学生自己的 rollout，把这段「策略变化」蒸馏过去。如果策略变化真能跨模型迁移，团队就不必让每个更大的模型都从头付一遍完整的探索成本，后训练扩展会便宜不少。

来源：[Direct On-Policy Distillation 论文](https://huggingface.co/papers/2607.05394)

### 搜索代理把进度从提示词搬到系统层

同样是研究侧的单层论文信号。SearchOS 用关系模式、证据图、覆盖图和失败记忆来存多代理检索的进度，让中间件接管证据处理、上下文、预算和行为防护；它把多代理检索建模成带引用的关系模式补全，再把证据、覆盖、失败和预算管理搬到一个显式的持久层。开放域检索最容易栽在长历史里：重复搜、丢了覆盖状态、预算烧光。把进度外置成共享的系统状态，失败就能看见，证据能追溯，协作也更稳。

来源：[SearchOS-V1 论文](https://huggingface.co/papers/2607.15257)

## 最后

这周没有那种一眼记得住的发布，但可能比很多热闹的周更值得记。harness 要能读、长任务要能一步步验、上传行为要能查、浏览器要能闭环，这几件事拼在一起，问的其实是同一句话：你凭什么信它干成了。

对使用者的要求也跟着变了。以前选型看能力，现在得多看一层：它的行为你能不能追溯，它的过程你能不能验证，它的数据流你能不能查清。这三样今天大多还得自己动手确认，产品默认不会给你。

这就是我这周看到的 AI 信号。
