最近我越来越明显地感觉到，AI 工作流里有一个成本很容易被忽略。

不是订阅费。

也不是 token。

而是一个任务刚刚跑热之后，你有没有趁着它还热，把它往前推完。

这个感觉在我同时开 Claude、Codex、ChatGPT、浏览器调研、文档整理的时候特别明显。表面上看，我开了很多条线，一个在写文章，一个在跑代码，一个在查资料，一个在改方案，好像效率很高。

但实际经常发生的是：每一条线都刚刚进入状态，我人就切走了。

半小时之后再回来，AI 可能还在同一个 session 里，聊天记录也还在，但我已经不在那个状态里了。我得重新看它做到哪一步、我刚才想要什么、下一步应该怎么接。有时候还要重新补目标、补约束、补验收标准。

这一刻浪费掉的，不只是模型的缓存。

还有我自己的注意力。

## 先把技术口径说清楚

这篇文章不是要把 Claude 或 Codex 的缓存机制写成一个确定教程。发布前我特地查了一遍官方文档，结论反而让我觉得，文章更应该写工作方法，而不是写机制结论。

几个可以确认的事实是：

Anthropic 的 [Prompt caching 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)里，默认 cache lifetime 是 5 分钟，也提供 1 小时 cache duration，但那是 Claude API 层的 prompt caching 机制。

[Claude Code 的 prompt caching 文档](https://code.claude.com/docs/en/prompt-caching)说得更细：用 Claude 订阅登录 Claude Code 时，主会话会自动请求 1 小时 TTL；如果用 API key 或第三方 provider，默认是 5 分钟，也可以在支持场景下显式开启 1 小时。它还特别提到，subagent 即使在订阅场景里也使用 5 分钟 TTL。

OpenAI 的 [Prompt caching 文档](https://developers.openai.com/api/docs/guides/prompt-caching)里也写了 API 层的缓存保留策略：in-memory prompt cache 通常在 5 到 10 分钟不活跃后仍可能有效，最长可到 1 小时；支持的模型还可以用更长的 extended retention。

但这些都不能直接写成：

**Claude Pro 聊天只记 5 分钟。**

也不能写成：

**Codex 产品里的 session 热度窗口就是 5 到 10 分钟。**

更不能写成：

**Claude Max 买到的是更长缓存 TTL。**

官方对 [Claude Max](https://support.claude.com/en/articles/11014257-about-claude-s-max-plan-usage) 的说法是更高的 session 使用额度，5x 或 20x more usage per session；同时单个聊天的 context window 仍然是 200K。换句话说，Max 更像是买到更多连续使用空间，而不是官方承诺更长缓存。

所以我现在更愿意把“上下文热度”定义成一个工作流概念：

> 一个 AI session、一个任务目标、一个上下文包，和我自己的注意力，在同一段时间里保持对齐的程度。

这个东西不是一个官方按钮，但它会非常真实地影响工作体验。

## 隐藏成本一：缓存不只是省钱，也是在省等待

以前我看 prompt caching，第一反应是省 token、省钱。

后来用多了才发现，它还在省等待。

一个长任务里，系统提示、项目背景、工具定义、文件结构、已经读过的材料，很多内容其实是重复出现的。如果这些前缀能命中缓存，下一轮会更快，也更省额度。反过来，如果缓存没命中，模型不是“忘了”，但它可能要重新处理一大段东西。

这对写代码、读仓库、改方案、整理长文档这类任务很明显。

你以为自己只是晚回来二十分钟。

但对一个长上下文 agent 来说，这可能意味着下一轮要重新吃一大块上下文，重新付一次延迟、额度和计算成本。

这个成本不一定显示成一个很直观的账单，但它会变成一种感觉：

“怎么这次接得没刚才顺？”

“怎么它又开始重新解释背景？”

“怎么只是继续一步，额度掉得这么快？”

这里真正要避免的，不是每一次 cache miss。

那不现实。

真正要避免的是，把一个已经跑热的任务频繁放冷。

## 隐藏成本二：上下文还在，但目标不一定还在

很多时候，聊天记录还在。

但任务目标已经散了。

比如我让 Codex 读一个项目，刚刚让它把目标、边界、文件结构都理顺。它正准备改第一处代码，我突然切到另一个文章草稿。半小时后回来，我看到的是一长串输出。

理论上，它知道自己做到了哪。

问题是我不知道了。

我得重新判断：

- 它刚才的理解是不是对的？
- 它下一步要改哪里？
- 我有没有答应它可以继续？
- 这个方向还是不是我想要的？

这时候最容易发生一种低效交互：我不想认真读完前文，就随手回一句“继续”。

然后任务开始漂。

AI 并不是不能继续，而是我没有把目标重新拿稳。它只是在顺着上一段对话往前走，但我已经忘了自己刚才真正关心什么。

所以“上下文热度”不只是模型侧的缓存，也包括人的任务记忆。

人一旦丢了当前状态，再强的模型也会被你带偏。

## 隐藏成本三：多线程看起来忙，实际可能很碎

多开 AI session 的诱惑很大。

一个 session 查资料。

一个 session 写文章。

一个 session 跑代码。

一个 session 做方案。

看起来像一个人在同时指挥四个小团队。

但我现在会更谨慎地看这件事。因为 AI 可以并行，人不一定可以。

如果每条线都需要我判断方向、读输出、做取舍、给下一步，最后瓶颈还是我自己。更糟的是，每次切换都会带走一点任务手感。

写文章的时候，语气刚刚进入状态，被另一个代码 session 叫走。

改代码的时候，文件结构刚刚想清楚，又切去看调研结果。

做方案的时候，客户问题刚刚在脑子里成形，又跑去处理另一个工具报错。

每次都只切几分钟，但每次回来都要重新热身。

这就是 AI 多线程最容易让人误判的地方：

> session 开得多，不等于推进得多。

真正有价值的不是同时开几条线，而是哪条线被推到了一个稳定节点。

## 我现在更倾向于用 Go 的方式跑长任务

这里的 Go 不是编程语言，而是一种工作方式。

我会尽量在一个长任务开始前，把目标、背景、约束、验收标准讲清楚，然后让 AI 连续推进一段完整工作，而不是每两分钟回来问我一次。

尤其是适合 agent 的任务，我现在更愿意这样启动：

1. 先说清楚我要什么。
2. 让它自己读上下文。
3. 让它执行一轮。
4. 让它自查。
5. 让它最后报告当前状态、改了什么、下一步是什么。

这样做的好处不是“省事”。

而是减少中间反复冷却和重启。

如果我知道自己接下来 30 分钟没法认真看它，我就不应该把任务拆成很多需要我确认的小碎片。要么让它一次跑到一个明确节点，要么先不要启动这条线。

这对写作也一样。

一篇文章如果刚刚找到语气，最好就顺着写完第一版。不要刚写出开头就切去查一个细枝末节。查资料当然重要，但查资料应该服务于这篇文章，不应该把这篇文章打散。

## 离开前，让 session 留下一句话

我现在觉得，多线程 AI 工作里最有用的小习惯之一，是离开前让 AI 留一个 checkpoint。

不用长。

就三件事：

- 当前目标是什么；
- 已经完成到哪里；
- 下一步最小动作是什么。

这句话不是给 AI 看的。

主要是给我自己看的。

因为我回来之后最怕的不是 AI 不知道上下文，而是我自己不知道该怎么接。

如果离开前留下了清楚的 checkpoint，回来时就不是在一大段对话里找感觉，而是直接看下一步。

这比“继续”两个字可靠得多。

“继续”看似省时间，实际把判断权交给了惯性。

而 checkpoint 会把判断权拿回来。

## 那订阅升级到底买到了什么

这件事也让我重新看订阅升级。

以前我会很容易把升级理解成“更聪明”“更强”“更高级”。

但现在我觉得，对高频用户来说，升级很多时候买的是三件更朴素的东西：

第一，更多用量。

第二，更少中断。

第三，更适合连续工作的空间。

Claude Max 官方讲的是更高 session 使用额度。Codex 的官方说明里，也会把任务复杂度、长时间任务、需要保持更多上下文的 extended sessions 和使用量消耗联系起来。它们都在提醒同一件事：长程 AI 工作不是免费悬浮在空中的，它会吃额度、吃上下文、吃人的注意力。

所以更高订阅有时确实能减少摩擦。

但它解决不了一个问题：

如果我自己把每条线都切碎，给再多额度，也只是让我更大规模地切碎。

这也是我之前写 AI 订阅时一直想提醒自己的事：升级之前，先确认自己是不是已经有了稳定场景。

如果场景稳定，升级是生产力投入。

如果场景不稳定，升级只是给冲动找理由。

## 我给自己的几个规则

写完这篇之后，我会给自己留几个很具体的规则。

第一，一天最多只保留一条真正的深水主线。

可以让别的 agent 查资料、跑辅助任务，但当天最需要我判断和表达的，只选一条。

第二，每个重要 session 启动时先写目标。

目标不清楚，不要急着让 AI 跑。否则它跑得越快，偏得也越快。

第三，离开前必须留 checkpoint。

当前状态、下一步、阻塞点，三句话就够。

第四，不要把“继续”当成默认回复。

回来后先问：这条线现在还值得继续吗？如果值得，再继续。

第五，把缓存冷掉当成一个提醒。

如果一个任务冷掉以后，我完全不想重新热起来，可能说明它本来就没那么重要。

## 最后

AI 工作流里的隐藏成本，不只是 token。

还有缓存命中。

还有上下文重建。

还有等待。

还有我自己的注意力切换。

工具越强，这个问题反而越明显。因为工具可以同时开很多条线，但人的判断力还是需要一条一条地落下去。

所以我现在对多线程 AI 工作的看法变得更简单：

可以并行收集信息。

可以并行跑一些低耦合任务。

但真正重要的任务，最好连续推进到一个稳定节点。

不要让每个 session 都停在“快要开始真正有价值”的地方。

那不是效率。

那只是把很多已经热起来的上下文，一次次放冷。
